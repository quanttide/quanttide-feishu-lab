# 招聘流程调度器（设计）

围绕 `tests/fixtures/flows/recruitment.yaml` 与本地已装的 `lark-cli`，做一个读 YAML、按状态机推进流程的程序，代替 `qtrecurit-cli` 里那些写死的命令。实验室验证时走 mock。

## 一、要解决的问题

`qtrecurit-cli` 把招聘流程的每一步写成了一个命令（同步邮箱、发问卷、发邀请、发考试），每个命令里硬编码了邮箱、文件夹、表列、模板。**流程等于命令的排列组合**——要调流程就得改代码。

现在流程已经写成了数据（`tests/fixtures/flows/recruitment.yaml`），差一个**执行器**：它读那份 YAML，把「什么事件发生 → 做哪一步 → 怎么算过」跑起来。跑通之后，调流程就是改 YAML。

## 二、第一道关口：触发要从「话」变成「条件」

现有 YAML 的触发是写给人看的话：

```yaml
- 从: 二维码已发
  到: 已进群
  触发: 群成员名单里出现该邮箱
```

程序看不懂这句话。所以 YAML 要扩一层：**每条迁移的触发由「一句话」补一个「一条检查」**——检查是一段可跑的东西（一条能力调用 + 一个判断），话留着给人读，检查给程序跑。

```yaml
- 从: 二维码已发
  到: 已进群
  触发: 群成员名单里出现该邮箱
  执行者: 系统
  检查:
    能力: read_group_members  # 能力名，不是命令
    成立: 包含该候选人邮箱
```

同一条迁移里，「人 / 系统」这类执行者描述也照此办理：**执行者说谁干，检查说什么时候干**。

副作用同此办理：原来只是一句话（「记发送时间」），现在迁移要真做的事再补一个「一条动作」——
一个能力调用 + 一段参数。执行器推这条迁移之前先做动作，**做失败就不挪格**；话留着给人读，
动作给程序跑。发群二维码就是这么发出去的：

```yaml
- 从: 投递
  到: 二维码已发
  触发: 收到投递，直接发群二维码
  执行者: 系统
  动作:
    能力: send_mail
    参数:
      to: "{{候选人.邮箱}}"
      subject: 量潮实训基地 · 群二维码
      body: 你好，扫码直接进群（群二维码见附件）。
      attachments: [群二维码.png]
  副作用: 记发送时间
```

不写动作的迁移照旧只挪格（副作用那句话仍留给人读）。

## 三、能力层：YAML 只认能力，不认命令

YAML 里**不出现任何 lark-cli 命令**，只出现能力名。能力是流程对外的需求清单：

| 能力 | 干什么 | 真实实现（lark-cli） | mock 实现 |
| :-- | :-- | :-- | :-- |
| 读邮件 | 按文件夹、按游标拉邮件与附件 | `mail +triage` / `mail +messages` | 读夹具目录 |
| 读问卷记录 | 读调研表 | `base +record-list` | 读夹具 JSON |
| 读群成员 | 读群成员名单 | `im chat.members` | 读夹具 JSON |
| 发邮件 | 发群二维码、问卷、邀请、凭证 | `mail +send` | 写进 `outbox/` |
| 写回 | 写台账、标记状态列 | `base +record-update` | 写夹具文件 |

**mock 就是这张表的第二列换成第三列**——换掉的是实现，不是流程。`--mock` 一开，同一份 YAML 用夹具跑；关掉，同一份 YAML 打真飞书。这也是为什么 YAML 里不能写命令：写了就没法换。

mock 分两层，读同一批 `tests/fixtures/`，不互相取代：资源层替身（`feishu/resources/mock.py`）直读夹具，给 runner 用；CLI 层 `packages/mock` 是个假 `lark-cli`——资源层真实现（`feishu/resources/real.py`，子进程调 `lark-cli`）把它 PATH 到前面就离线自测，代码一份不改，PATH 里是真 `lark-cli` 就打真飞书。流程能力层（`feishu/client.py`）只负责包一层，与换哪种实现无关。设计见 `packages/mock/README.md`。

## 四、状态落在哪

流程要有「一个候选人现在在哪一格」的记录。三条规矩：

1. **状态存在本地文件**（`tests/fixtures/state/recruitment.json`），一条候选人一条记录：当前状态、进入时间、走过的迁移。
2. **位置不进模型**：状态文件与夹具目录的位置都由启动参数给，缺省在当前工作目录下。同一份 YAML 在哪都能跑。
3. **状态可重建**：能从飞书侧的原始数据（邮件、表记录、群成员）重放出来。本地状态是缓存，不是事实源——事实在飞书那边。

## 五、一轮跑什么

程序不做常驻服务，**一轮一跑，跑完退出**：

```
读 YAML → 建状态机（状态 + 迁移 + 检查）
      → 读本地状态（没有就按收集范围初始化：谁在收件箱里，谁就是一个新候选人）
      → 对每个人、每条迁移：检查成立吗？
          成立 → 执行该迁移（调能力、记副作用、改状态）
          不成立 → 跳过
      → 写回状态，打印这一轮干了什么
```

一次只推一步还是把能推的都推完，由参数定（`--step` / `--drain`）。默认 `--step`：一轮只推一步，像 `qtcloud-work task --next` 那样一条一条走，看得清。

## 六、命令形态

```
recruitment run      # 跑一轮（默认一步）
recruitment status   # 打印所有候选人当前在哪一格
recruitment replay   # 从飞书侧原始数据重建本地状态
recruitment run --mock --fixtures tests/fixtures/   # 实验室：走夹具
```

与 `qtcloud-work task` 的手感对齐（`--new` 开单、`--next` 走一步），因为它已经证明了这个形状对 AI 友好：每步有产物、每步留账、可中断可续跑。

## 七、怎么算跑对了

实验室的判据，全部可跑：

1. **可重复**：同一份 YAML + 同一批夹具，跑两遍，状态文件与输出**逐字节相同**。
2. **换实现不换流程**：同一份 YAML，`--mock` 与打真飞书，迁移顺序与状态变化一致（真飞书那侧只比迁移序列，不比内容）。
3. **等价于旧 CLI**：`qtrecurit-cli` 的拉邮件、发邮件在新流程里有对应迁移（2026-10 简化后问卷不再前置，拉问卷留给评估报告）；跑完一个虚构候选人的完整旅程（投递 → 收到群二维码 → 扫码进群），全程不用手工补数据。
4. **改流程不改代码**：把 YAML 里「无响应的天数 N」从 7 改成 3，重跑，行为跟着变；代码零改动。

## 八、不做什么

- 不做常驻服务、不连数据库、不做 webhook 订阅——飞书侧没有推送就给轮询，够用。
- 不重写发邮件、发邀请这些动作：它们是**能力**，还是通过 `lark-cli` 干，runner 只负责在正确的时机叫它们。
- 不把流程判断写进代码：任何「这一步该不该走」的判断都必须在 YAML 的检查里，代码里不许有招聘的知识。
- 不碰其他仓库：本轮只在实验室里做。

## 九、落地顺序

1. 定能力清单（第三节那张表，先只留跑通最小闭环要用的四种：读邮件、读问卷记录、读群成员、发邮件）。
2. 写 mock 能力 + 夹具（三五个虚构候选人，覆盖投递 / 二维码已发 / 已进群三格）。
3. 写 runner 骨架：读 YAML、建状态机、`--step` 推一步、状态落盘。
4. 真对接：子进程能力已就绪（`feishu/resources/real.py`），给真 base-token / table-id / chat-id 与权限，对着真邮箱与真表跑一轮，核第三条判据。
5. 之后再谈把 runner 固化到哪一层——它是原型，不是产品。
